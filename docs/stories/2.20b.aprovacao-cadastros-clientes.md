## Story

**Como** Secretária ou Gestão que recebe cadastros de clientes pendentes,
**Quero** uma tela no módulo Clientes para listar, conferir a identidade e aprovar ou recusar cada cadastro, com auditoria de quem decidiu e quando,
**Para que** nenhum dado seja liberado a um solicitante sem confirmação de que ele é o titular do CPF (R-17), evitando que um terceiro assuma a identidade de um cliente real.

---

## Escopo

**Dentro do escopo (IN):**
- Tela de cadastros pendentes no módulo Clientes (FR24).
- RPCs `aprovar_cadastro_cliente`, `recusar_cadastro_cliente`, `revogar_acesso_cliente`.
- Recuperação assistida de senha (`gerar_codigo_redefinicao` + ação `redefinir` da Edge Function `cliente-auth`).
- Interpretação registrada do procedimento de conferência de identidade (OQ-5).

**Fora do escopo (OUT):**
- Rota pública de cadastro e `ProtectedRoute`/`ClienteContext` — Story 2.20c.
- Job de descarte automático de cadastros expirados/recusados (retenção LGPD) — Story 2.20c.

## Acceptance Criteria

1. É criada a tela de **cadastros pendentes** no módulo Clientes (FR24), visível para `admin`/`secretaria` (Regra 14 — Clientes é tela compartilhada), que lista os cadastros com `status = 'pendente'`, permite conferir os dados informados contra o registro existente em `public.clientes` de mesmo CPF (quando houver), e oferece as ações **aprovar** e **recusar**.
2. É criada a RPC `public.aprovar_cadastro_cliente(cadastro_id text, cliente_id_existente text DEFAULT NULL)` (ADR-007 §3.6) — `SECURITY DEFINER`, `SET search_path = ''`, primeira linha `papel_usuario() IN ('admin','secretaria')` (senão erro); grants `REVOKE ... FROM PUBLIC`, `GRANT ... TO authenticated`. A função: (a) exige `identidade_conferida = true` e `metodo_conferencia` preenchido (R-17) — a UI não permite aprovar sem marcar esses campos; (b) faz `SELECT ... FOR UPDATE` no cadastro (deve estar `pendente`); (c) resolve vínculo sem duplicidade (NFR19.6): se existe `clientes` com os mesmos dígitos de CPF e `auth_user_id IS NULL`, vincula; se já vinculado a outra conta, retorna **erro de conflito** para a Secretaria resolver manualmente (nunca sobrescreve); se não existe, cria o `clientes` a partir dos dados do cadastro; (d) `UPDATE auth.users SET raw_app_meta_data = raw_app_meta_data || '{"role":"cliente"}'`; (e) marca `status = 'aprovado'`, `decidido_por = auth.uid()`, `decidido_em = now()`.
3. É criada a RPC `public.recusar_cadastro_cliente(cadastro_id, motivo)` — mesmas travas de papel e de `SELECT ... FOR UPDATE`; marca `status = 'recusado'`, `decidido_por`, `decidido_em`, `motivo_recusa`. **Decisão confirmada do proprietário (2026-09-24):** a conta do Supabase Auth associada (`cadastros_clientes.auth_user_id`) é **excluída imediatamente** na recusa (`admin.deleteUser`, chamado pela RPC via Edge Function auxiliar ou por uma função `SECURITY DEFINER` com acesso ao Auth Admin API — a critério do `@architect`/`@data-engineer` qual mecanismo usar, já que RPCs Postgres puras não chamam a Auth Admin API diretamente) — o cliente recusado não pode tentar `entrar` novamente com a mesma conta. O **registro** de `cadastros_clientes` (dados pessoais do cadastro) **não** é excluído junto com a conta — permanece retido por **3 anos** para fins de auditoria (histórico de quem foi recusado, por quem e por quê). Como o índice único parcial de `cadastros_clientes` cobre apenas `status IN ('pendente','aprovado')` (Story 2.20a AC1), um registro `recusado` **não impede** um novo cadastro do mesmo CPF no futuro — a Edge Function `cliente-auth` (ação `cadastrar`) cria uma nova conta e um novo registro `pendente` normalmente, sujeito a nova conferência de identidade.
4. É criada a RPC `public.revogar_acesso_cliente(cliente_id)` — `admin`/`secretaria`: remove o papel (`app_metadata.role`) e zera `clientes.auth_user_id` (ex.: acesso concedido por engano). A aprovação/revogação vale a partir do próximo login do cliente (o JWT só carrega o papel novo quando é emitido de novo); como uma conta pendente/revogada não recebe sessão (Story 2.20a AC6 "entrar"), não existe sessão "velha" a invalidar explicitamente.
5. **Procedimento de conferência de identidade confirmado pelo proprietário (OQ-5, 2026-09-24):** após o cadastro por CPF, a Secretaria confirma a identidade do solicitante **contatando-o pelo telefone já cadastrado** em `public.clientes` (quando o CPF já existir) antes de marcar `identidade_conferida = true` e preencher `metodo_conferencia = 'telefone_cadastrado'`. Quando o CPF **não existir** em `public.clientes` (cliente novo, sem cadastro presencial prévio), o procedimento de conferência para esse caso permanece **em aberto** — a UI deve permitir registrar `metodo_conferencia` como texto livre ou uma segunda opção enumerada (ex.: `'presencial'`) até que o `@po` formalize o procedimento para clientes totalmente novos.
6. Aviso opcional ao cliente pelo WhatsApp oficial (FR18) após a decisão: mensagem informando aprovação ou recusa, **sem** senha, código de acesso ou link com credencial (NFR19, ADR-007 §3.6).
7. **Recuperação assistida de senha (MVP, ADR-007 §3.8):** é criada a RPC `public.gerar_codigo_redefinicao(cliente_id)` — acessível a `admin`/`secretaria` a partir da tela de clientes, após a Secretaria conferir a identidade presencialmente ou por telefone — que gera um código de 8 caracteres, uso único, validade de 15 minutos, gravado **como hash**. O código é entregue presencialmente ou lido por telefone — **nunca por WhatsApp** (FR18). É implementada a ação `redefinir` da Edge Function `cliente-auth` (CPF + código + nova senha + CAPTCHA), que valida o hash, aplica `admin.updateUserById(..., { password })` e invalida o código; resposta neutra em qualquer caso. Recuperação self-service por e-mail real fica **fora do MVP** (a conta Auth usa e-mail sintético).
8. Toda decisão (aprovar/recusar), o autor (`decidido_por`) e a data/hora (`decidido_em`) entram na trilha de auditoria (NFR16) via `fn_audit_trigger()` (Story 2.2), já anexada a `cadastros_clientes` (Story 2.20a).
9. Teste automatizado cobre: aprovação vinculando a um cliente existente sem duplicar; aprovação criando cliente novo; tentativa de aprovar sem `identidade_conferida = true` é rejeitada; recusa **com exclusão imediata da conta Auth e registro `recusado` retido**; tentativa de `entrar` após recusa falha (conta não existe mais); novo cadastro do mesmo CPF após uma recusa anterior é aceito normalmente (índice único parcial não bloqueia); revogação de acesso; geração e uso do código de redefinição (uso único, expiração de 15 min); RPCs rejeitam chamadas de papéis diferentes de `admin`/`secretaria`.
10. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### FR24 — o que a tela precisa fazer (PRD v1.4)
1. lista os cadastros pendentes; 2. confere os dados informados pelo cliente com o registro existente em `public.clientes` de mesmo CPF, quando houver; 3. aprova (vinculando ao existente ou criando novo, nunca duplicando) ou recusa; 4. opcionalmente avisa o cliente pelo WhatsApp oficial. Perfis: Gestão e Secretaria (Regra 14 — Clientes é tela compartilhada, diferente de Funcionários).

### OQ-5 — decisões confirmadas pelo proprietário (2026-09-24)
- **Local da tela de aprovação:** dentro do módulo Clientes da Gestão/Secretaria (não uma tela separada dentro do portal do cliente) — interpretação já registrada no PRD v1.4 como a leitura mais provável da fala do proprietário.
- **Procedimento de conferência de identidade (confirmado):** contato **pelo telefone já cadastrado** em `public.clientes`, quando o CPF já existir (ver AC5). O procedimento para CPF **totalmente novo** (sem registro prévio em `clientes`) permanece em aberto — não inventar um procedimento equivalente sem confirmação do `@po`.
- **Retenção de dados de cadastro:** 3 anos para cadastros **aprovados e recusados** (LGPD) — a exclusão da **conta Auth** de um cadastro recusado é **imediata** (AC3), mas o **registro** de `cadastros_clientes` permanece pelos 3 anos; cadastros `pendente` sem decisão expiram em 30 dias (job de retenção implementado na Story 2.20c).

### Vínculo sem duplicidade — não reinventar a regra
A lógica de "existe cliente com o mesmo CPF e sem vínculo → vincula; já vinculado a outra conta → erro de conflito; não existe → cria" é do ADR-007 §3.6 e não deve ser simplificada — um erro aqui duplicaria clientes ou sequestraria o cadastro de outra pessoa.

### Arquivos afetados
- **[NEW]** tela de cadastros pendentes (módulo Clientes — confirmar caminho exato ao iniciar, ex.: `src/pages/dashboard/clientes/CadastrosPendentesPage.jsx`)
- **[NEW]** `supabase/migrations/{timestamp}_rpc_aprovacao_cadastro_cliente.sql`
- **[NEW]** `supabase/migrations/{timestamp}_rpc_recuperacao_assistida_cliente.sql`
- **[MODIFY]** Edge Function `cliente-auth` (adicionar ação `redefinir`)
- **[NEW]** `tests/unit/aprovacaoCadastroCliente.test.js`

### Riscos
- Se a Secretaria aprovar sem de fato confirmar a identidade (ignorando a UI de conferência), o risco R-17 (cadastro com CPF de terceiro) se materializa — a UI deve tornar o campo `identidade_conferida` explícito e não pré-marcado.
- O procedimento de conferência por telefone (AC5) depende de o telefone cadastrado ser realmente do titular — se o telefone também foi fornecido por um impostor no cadastro original de balcão, a conferência falha silenciosamente; risco residual aceito nesta rodada, a ser revisitado se houver incidente.
- O procedimento de conferência para CPF totalmente novo não está definido — até que o `@po` formalize, a Secretaria precisa de uma alternativa operacional (ex.: presencial) documentada na UI, para não travar a aprovação nem incentivar um atalho inseguro.
- A exclusão imediata da conta Auth na recusa depende de um mecanismo de acesso ao Auth Admin API a partir de uma RPC — se implementado incorretamente (ex.: RPC tentando chamar a Auth API diretamente do Postgres, o que não é suportado), a exclusão pode falhar silenciosamente; validar com teste de integração real, não apenas mock.
- A recuperação assistida exige presença física ou ligação telefônica — se a Secretaria entregar o código por WhatsApp por engano (violando FR18), a segurança do fluxo é comprometida; reforçar isso no texto da UI, não apenas na documentação.
