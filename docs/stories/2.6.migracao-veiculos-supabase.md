# Story 2.6: Migração de Veículos para Supabase Postgres (com Extração de Repositório Dedicado)

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** B — Cadastros
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @data-engineer
**Dependências:** Story 2.5 (Clientes — FK `veiculos.cliente_id`)

---

## Story

**Como** secretária ou administrador da oficina,
**Quero** que o cadastro de Veículos vire uma entidade própria persistida em `public.veiculos`, com vínculo real de chave estrangeira ao cliente,
**Para que** a frota de um cliente seja consultável independentemente de onde o veículo foi cadastrado, sem depender de arrays embutidos no objeto do cliente em `localStorage`.

---

## Acceptance Criteria

1. É criado `src/repositories/veiculosRepository.js` (novo — hoje **não existe** um repositório dedicado; a tela `VeiculosPage.jsx` lê `carregarTodosVeiculosDaFrota()` diretamente de `src/constants/mockClientesVeiculos.js`, o que viola FR9), expondo no mínimo: `carregarVeiculos()`, `obterVeiculoPorId(id)`, `obterVeiculoPorPlaca(placa)`, `salvarVeiculo(veiculo)`, `excluirVeiculo(id)`, `obterVeiculosDoCliente(clienteId)` — todas assíncronas (`Promise`), seguindo o padrão *Async Contract First* (ADR-002).
2. `src/pages/dashboard/veiculos/VeiculosPage.jsx` e `src/components/estacionados/ModalEstacionarVeiculo.jsx` passam a consumir `veiculosRepository.js` em vez de importar `carregarTodosVeiculosDaFrota()` diretamente de `src/constants/mockClientesVeiculos.js`.
3. `clientesRepository.js` (Story 2.5) tem sua função `obterVeiculosDoCliente()` atualizada para delegar para `veiculosRepository.obterVeiculosDoCliente()`, eliminando a leitura do array `veiculos` embutido no objeto de cliente.
4. O repositório grava/lê em `public.veiculos` via Supabase quando configurado (helpers da Story 2.1), com fallback para `localStorage` (nova chave dedicada, ex.: `dev_oficina_veiculos`, migrando na primeira leitura os veículos hoje embutidos em `MOCK_CLIENTES_VEICULOS`/`dev_oficina_clientes` — rotina de migração defensiva em `getStoredVeiculos()`, seguindo o padrão já usado no projeto de "ler formato antigo uma vez, regravar no formato novo").
5. Mapeamento de campos cobre: `placa` (chave natural, `UNIQUE` no banco), `marca`, `modelo`, `ano`, `combustivel`, `cor`, `km_atual`, `observacoes`, `cliente_id`.
6. `salvarVeiculo()` valida (no cliente, como já ocorre hoje) e trata o erro de `placa UNIQUE` do Postgres com mensagem amigável via `sonner` caso duas oficinas... (N/A, mono-tenant) — caso o mesmo veículo seja recadastrado, mensagem clara "Placa já cadastrada para outro cliente".
7. RLS de `public.veiculos` usa exclusivamente `public.papel_usuario()`: `admin` acesso total; `secretaria` `SELECT`/`INSERT`/`UPDATE` (políticas já existentes desde `20260924130000`); `mecanico` apenas `SELECT`. Nenhuma política anônima.
8. Teste automatizado cobre CRUD com Supabase mockado, fallback local, migração defensiva do formato antigo (veículo embutido em cliente) e busca por placa.
9. Telas desktop (`VeiculosPage.jsx`) e mobile (`src/pages/dashboard/veiculos/mobile/MobileVeiculosPage.jsx`) verificadas — nenhuma alteração estrutural além da troca da fonte de dados.
10. `npm run lint` e `npm test` sem novos erros; `veiculosRepository.js` ≤ 400 linhas.

## Dev Notes

### Estado atual do código (importante — não é o que o PRD/ADR-002 supõe)
Diferente do que ADR-002 (§3.3) sugere implicitamente, **não existe hoje um `veiculosRepository.js`**. Veículos vivem como um array `veiculos` dentro de cada objeto de cliente em `src/constants/mockClientesVeiculos.js` (397 linhas), e a tela `VeiculosPage.jsx` (bem como `ModalEstacionarVeiculo.jsx` e `mockManutencaoPreventiva.js`) importa `carregarTodosVeiculosDaFrota()` **diretamente desse módulo de constants**, sem passar por nenhum repositório — uma violação preexistente de FR9 que esta story corrige como efeito colateral necessário para a migração.

### Tabela-alvo
`public.veiculos` (migration `20260921_initial_schema.sql` §3): `id TEXT PRIMARY KEY`, `cliente_id TEXT REFERENCES clientes(id) ON DELETE CASCADE`, `placa TEXT UNIQUE NOT NULL`, `marca`, `modelo`, `ano TEXT`, `combustivel TEXT DEFAULT 'Flex'`, `cor`, `km_atual INTEGER`, `observacoes`, `created_at`, `updated_at`.

**Atenção ao `ON DELETE CASCADE`:** excluir um cliente hoje, no banco real, excluirá silenciosamente todos os seus veículos. Isso é uma mudança de comportamento em relação ao `localStorage` atual (onde exclusão de cliente e de veículo são operações independentes). Documentar esse comportamento na UI de exclusão de cliente (fora do escopo desta story — mas o `@dev` deve registrar como nota de atenção para a Story 2.5 ou para o backlog do `@po`, já que a Story 2.5 já foi drafted sem esse detalhe).

### RLS já existente
Idêntica à de `clientes` (ver Story 2.5 Dev Notes) — `"Admin total veiculos"`, `"Equipe le veiculos"`, `"Secretaria grava veiculos"`, `"Secretaria atualiza veiculos"` (migration `20260924130000`).

### Riscos
- `placa UNIQUE` pode rejeitar dados de teste/seed duplicados vindos do `localStorage` de ambientes de desenvolvimento antigos — a rotina de migração defensiva deve tratar conflito de forma não-destrutiva (logar e pular, não falhar silenciosamente o carregamento inteiro).
