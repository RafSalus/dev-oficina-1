**Status:** Ready for Review

**Autor:** River (@sm)  
**Executor:** Dex (@dev)  
**Quality Gate:** @qa  

---

## 1. Story Narrative

**Como** proprietário da oficina Mecânica Gabriel,  
**Quero** que o acesso ao ERP seja restrito a usuários autenticados, com controle de horário operacional e dispositivos autorizados,  
**Para que** dados sensíveis de clientes, veículos, faturamento e ordens de serviço fiquem protegidos contra acessos indevidos e funcionários acessem o sistema apenas durante o expediente de trabalho.

---

## 2. Acceptance Criteria (ACs)

- [x] **AC1:** Existe um componente `ProtectedRoute` que consome os contextos de autenticação já existentes (`AdminAuthContext`, `ClienteContext`, `MecanicoContext`), sem introduzir novas bibliotecas externas de autenticação.
- [x] **AC2:** Acesso deslogado a qualquer rota sob `/gestao/*` (exceto rotas públicas `/gestao/entrar`, `/gestao/recuperar-senha`, `/gestao/acesso-negado`, `/gestao/mfa/*`) redireciona imediatamente para `/gestao/entrar`.
- [x] **AC3:** Acesso deslogado a `/secretaria/*` e `/mecanico/*` redireciona para as respectivas páginas de autenticação do portal.
- [x] **AC4:** Acesso a `/cliente/*` sem identidade válida de cliente estabelecida redireciona para `/cliente/entrar`. O fallback padrão que expunha dados anônimos (`ClienteContext.jsx:19-20`) foi eliminado.
- [x] **AC5:** A rota originalmente pretendida pelo usuário é preservada na query string (`?returnUrl=...`), garantindo retorno automático à tela após o login bem-sucedido.
- [x] **AC6:** Durante a verificação de sessão, o componente exibe um estado sóbrio de carregamento (spinner/skeleton discreto em azul `#0284c7` sobre fundo neutro), sem piscar a tela de login nem vazar conteúdo protegido.
- [x] **AC7:** As 9 rotas públicas por design — `/`, `/cliente/entrar`, `/gestao/entrar`, `/gestao/recuperar-senha`, `/gestao/acesso-negado`, `/cotacao/:id`, `/aprovacao/:id`, `/orcamento/:id`, `/vistoria/:id` — permanecem 100% acessíveis sem autenticação.
- [x] **AC8:** A rota `/gestao/acesso-negado` passa a ser renderizada quando o usuário autenticado tentar acessar área para a qual não possua papel autorizado.
- [x] **AC9 (Regra de Horário Comercial):** Usuários com perfil `secretaria` e `mecanico` só podem acessar o sistema nos dias operacionais entre **08:00 e 19:00**. Tentativas fora dessa janela exibem tela de aviso sóbria informando o encerramento do expediente.
- [x] **AC10 (Pareamento de Dispositivo na Oficina):** O primeiro acesso dos perfis operacionais exige autorização prévia de dispositivo (`dev_oficina_device_token`), registrando que a máquina foi liberada na oficina.
- [x] **AC11 (Bypass do Administrador):** O usuário com perfil `admin` possui bypass permanente das restrições de horário e de rede, com **acesso irrestrito 24/7 de qualquer local**, condicionado à autenticação de dois fatores (MFA AAL2).
- [x] **AC12 (Proibição de Auto-cadastro):** Proibido qualquer botão, link ou fluxo de auto-cadastro público de cliente (`signUp`).

## 3. Integration Verification (IVs)

- [x] **IV1:** Fluxo de autorização e guarda testado nos 4 portais (Gestão, Secretaria, Mecânico e Cliente) via suite de testes automatizada em `tests/unit/auth-guards.test.js` (15/15 testes passando).
- [x] **IV2:** Rotas públicas (`/cotacao/:id`, `/aprovacao/:id`, etc.) permanecem fora do guard e renderizáveis sem credenciais.
- [x] **IV3:** Teste de bloqueio de horário comercial (08:00 às 19:00 no fuso de Brasília) e dispositivo para equipe operacional vs bypass 24/7 para Administrador validado com sucesso.
