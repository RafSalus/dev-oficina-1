# Story 2.18: Fotos e Assinaturas de Vistoria no Supabase Storage

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** E — Ordem de Serviço Completa
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @architect
**Dependências:** Story 2.14 (OS — `id` UUID, pré-requisito da convenção de caminhos), Story 2.17 (acesso público por token — a vistoria é uma rota pública, a RPC `obter_vistoria_por_token` é consumida pela Edge Function desta story)

---

## Story

**Como** mecânico ou secretária que registra o checklist de entrada de um veículo,
**Quero** que fotos do checklist e a assinatura do cliente sejam enviadas para o Supabase Storage em vez de ficarem em base64 dentro do `localStorage`/Postgres, com URLs assinadas geradas por uma Edge Function dedicada,
**Para que** o sistema não estoure a quota de `localStorage` (Risco R-11 do PRD) nem infle desnecessariamente o banco Postgres, e para que o visitante anônimo da vistoria nunca receba uma URL pública permanente do bucket.

---

## Escopo

**Dentro do escopo (IN):**
- Bucket privado `vistorias` com políticas de `storage.objects`.
- Edge Function `acesso-publico-midia` para gerar URLs assinadas (5 minutos) a partir da RPC de token (Story 2.17).
- Convenção de caminhos `os/{os_id}/fotos/...` e `os/{os_id}/assinatura/...`.

**Fora do escopo (OUT):**
- Geração de URL assinada dentro de uma função Postgres — **tecnicamente impossível** (a assinatura é feita pela API do Storage com chave de servidor, não pelo Postgres); esta story corrige essa premissa incorreta de versões anteriores.
- Fila de sincronização offline persistente para uploads que falharem — fora de escopo (ADR-005 §2.3); a contingência é apenas em memória durante a sessão.

---

## Acceptance Criteria

1. É criado um **bucket privado do Supabase Storage** `vistorias` (nunca público), com `file_size_limit` e `allowed_mime_types` (`image/jpeg`, `image/png`, `image/webp`) configurados no bucket. O front comprime a imagem antes do upload (redução de quota, R-11).
2. **Convenção de caminhos:** `os/{os_id}/fotos/{uuid}.{ext}` e `os/{os_id}/assinatura/{uuid}.png`, onde `os_id` é o UUID de `ordens_servico.id` (pré-requisito entregue pela Story 2.14/ADR-005 §2.6 — portanto não adivinhável) e `{uuid}` do arquivo é gerado no cliente apenas para o nome do objeto.
3. São criadas as **políticas de `storage.objects`** (todas com `bucket_id = 'vistorias'`): `INSERT` e `SELECT` para `papel_usuario() IN ('admin','secretaria','mecanico')`; `UPDATE`/`DELETE` somente `admin` (a vistoria é evidência; substituir = novo objeto); **nenhuma política para `anon`**.
4. `checklist_entrada`/`fotos_entrada` (colunas `JSONB` já existentes em `ordens_servico`) passam a armazenar **caminhos** do objeto no Storage em vez do conteúdo binário/base64 da foto; `assinatura_cliente` (hoje `TEXT`, base64) segue o mesmo tratamento — grava o caminho, não o conteúdo.
5. É criado um módulo utilitário (ex.: `src/services/storageService.js`) com funções `uploadFotoVistoria(arquivo, osId)` e `uploadAssinaturaVistoria(dataUrlOuBlob, osId)`, retornando o **caminho** do objeto salvo (não uma URL — URLs são geradas sob demanda, nunca armazenadas).
6. O fluxo de checklist de entrada (`src/constants/checklistItems.js` — `carregarAssinaturaVistoria`/`salvarAssinaturaVistoria`) é atualizado para: (a) fazer upload da assinatura/fotos ao Storage no momento do registro, (b) gravar apenas o caminho no banco, (c) manter o comportamento local (base64 em `localStorage`) apenas quando `isSupabaseConfigured` for falso, seguindo a política fail-closed da Story 2.1 (sem fallback em falha de upload no modo remoto — ver AC8).
7. É criada a **Edge Function `acesso-publico-midia`** (ADR-006 §2.5), que: (a) recebe o token; (b) chama `public.obter_vistoria_por_token(token)` com o cliente `anon` (a validação, expiração e rate limit ficam na RPC — fonte única de verdade, Story 2.17); (c) com o cliente **service role**, gera `createSignedUrls` **somente para os caminhos devolvidos pela RPC**, com validade de **5 minutos**; (d) devolve dados + URLs, com resposta genérica em qualquer falha. A service role key existe só como secret da Edge Function (mesmo padrão de `criar-login-funcionario`); CORS restrito a `ALLOWED_ORIGINS`. A tela pública de vistoria (`VistoriaEntradaClientePage.jsx`, rota `/vistoria/:token`, Story 2.17) consome exclusivamente esta Edge Function — **nunca** chama `createSignedUrl()` diretamente nem acessa o bucket de outra forma. Para a equipe autenticada, o front usa `createSignedUrl()` diretamente (as políticas de `SELECT` do AC3 bastam).
8. **Falha de upload:** no modo remoto, a mídia pendente de upload fica **somente em memória** durante a sessão, com botão de reenvio e aviso explícito de que ainda não foi salva (`sonner`) — **não há persistência local** dessa contingência (ADR-005 §2.3 proíbe cache de dados pessoais persistente); nenhum `catch` de falha de upload é silencioso.
9. Teste automatizado (mock de `supabase.storage` e da Edge Function) cobre: upload bem-sucedido retornando caminho, comportamento em modo local, geração de URL assinada de curta duração via Edge Function, rejeição de acesso `anon` direto ao bucket.
10. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/constants/checklistItems.js` define `STORAGE_KEY_ASSINATURA_VISTORIA = 'dev_oficina_assinaturas_checklist'` e as funções `carregarAssinaturaVistoria(numeroOS)`/`salvarAssinaturaVistoria(numeroOS, registro)`. `ITENS_CHECKLIST_ENTRADA`, `FOTOS_VEICULO_TIPOS` e `ITENS_CHECKLIST_SAIDA` estão hoje **vazios** (`[]`) no código atual — esta story assume que isso é um placeholder aguardando definição de conteúdo e **não** inventa o conteúdo desses catálogos, apenas constrói a infraestrutura de armazenamento de foto/assinatura que os consumirá quando estiverem populados.

### Correção de premissa técnica (ADR-006 §3, alternativa rejeitada)
Uma versão anterior desta story previa a RPC `obter_vistoria_por_token` gerando `createSignedUrl` diretamente. Isso é **tecnicamente impossível**: uma função Postgres não tem acesso à API do Storage para assinar URLs — isso só pode ser feito por um cliente com a service role key, fora do banco. Por isso a Edge Function `acesso-publico-midia` existe: ela chama a RPC (fonte de verdade da validação de token) e, separadamente, assina as URLs dos caminhos retornados.

### `assinaturas_checklist` é uma das chaves de risco explícitas do PRD
Risco R-11 (`docs/prd.md` §4.5): "Quota de `localStorage` estoura antes do Epic 2 (fotos e assinaturas em `dev_oficina_assinaturas_checklist`)". Esta story é a mitigação definitiva desse risco.

### Janela operacional no upload — pendente (D4 não cobre Storage explicitamente)
O ADR-006 §2.4 registra como **PENDENTE (D4)** se a janela 08h-19h se aplica ao upload do mecânico/secretaria. A decisão do proprietário registrada nesta rodada (D4) cobre explicitamente "escrita em Veículos e Suprimentos" — **não menciona Storage/vistoria**. Esta story **não aplica** a janela operacional ao upload por ora (tratamento igual ao resto do fluxo de checklist de entrada, que já ocorre durante o atendimento); se o `@po`/`@architect` decidirem estender D4 ao Storage, isso é uma migration incremental de política futura.

### Riscos
- Upload de imagem em conexão 4G instável (mecânico em campo) pode falhar no meio do checklist — AC8 exige que isso não trave o fluxo; a experiência de "sincronizar depois" precisa ser clara para o usuário, sem prometer sincronização automática que não existe (sem fila persistente).
- A Edge Function `acesso-publico-midia` concentra a service role key — mesmo padrão de risco que `criar-login-funcionario`; qualquer bug nela expõe o bucket inteiro. Revisão de segurança obrigatória do `@architect`.
- A pendência de janela operacional (D4) para o Storage não resolvida nesta rodada pode exigir ajuste incremental futuro — registrado, não bloqueante.
