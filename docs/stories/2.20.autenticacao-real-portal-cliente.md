# Story 2.20: Autenticação Real do Portal do Cliente via Supabase Auth (FR18)

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** G — Portal do Cliente
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @architect
**Dependências:** Story 2.5 (Clientes), Story 2.14 (OS — visibilidade das próprias OSs do cliente)

---

## Story

**Como** cliente da oficina,
**Quero** ativar meu acesso ao portal `/cliente` através de um link de ativação enviado por WhatsApp e fazer login real com senha própria,
**Para que** apenas eu (e não qualquer visitante que abra o devtools) consiga ver minhas OSs e veículos — encerrando o contorno hoje existente na proteção do portal do cliente.

---

## Acceptance Criteria

1. `src/components/auth/ProtectedRoute.jsx` — bloco `if (portal === 'cliente')` — deixa de decidir acesso checando apenas `localStorage.getItem('dev_oficina_cliente_ativo')` (hoje trivialmente contornável: qualquer usuário pode gravar essa chave manualmente pelo console do navegador e obter acesso a `/cliente/*`) e passa a validar uma **sessão real do Supabase Auth** para o papel `cliente` (`app_metadata.role = 'cliente'`, seguindo o mesmo padrão `papel_usuario()` já usado para os demais perfis desde a Fase 0 de segurança).
2. `src/context/ClienteContext.jsx` deixa de resolver a identidade do cliente por busca em `MOCK_CLIENTES_VEICULOS`/`localStorage` e passa a obter o cliente ativo a partir da sessão Supabase Auth autenticada (via `auth.uid()` vinculado ao registro em `public.clientes`, exigindo uma coluna de vínculo, ex.: `clientes.auth_user_id UUID REFERENCES auth.users(id)`, análoga ao padrão já existente em `funcionarios.auth_user_id`).
3. É criado o fluxo de **ativação via WhatsApp** (FR18/OQ-2, decisão já aprovada no PRD §4.6): ao cadastrar um cliente presencialmente no balcão (Secretaria/Gestão), o sistema gera um link de ativação seguro (token de uso único com expiração — mesmo padrão de token opaco da Story 2.17, ou o fluxo nativo de convite do Supabase Auth `inviteUserByEmail`/magic link adaptado, a critério do `@architect`) e abre o WhatsApp oficial (`wa.me`) com a mensagem contendo o link, replicando o padrão de UX já usado (`Footer`, `ClientesPage`, `CotacaoAutoPecaPage`).
4. O cliente, ao acessar o link de ativação, define sua própria senha e a partir daí faz login normalmente em `/cliente/entrar` com e-mail/telefone + senha (a decidir qual identificador usar como login, dado que nem todo cliente PF tem e-mail cadastrado — **decisão de negócio a confirmar com `@po`/`@architect`**, já que o PRD não especifica o identificador de login do cliente).
5. **Autocadastro público continua terminantemente proibido** (FR17) — nenhuma rota ou botão de `signUp` é exposto em `/cliente/entrar`; a única forma de uma conta de cliente existir é criada a partir do balcão da oficina (Secretaria/Gestão), consistente com a Story 1.1 (AC10) já implementada no Epic 1.
6. RLS de `public.clientes` (e das tabelas que o cliente pode ler: `ordens_servico`, `veiculos`) ganha política adicional para o papel `cliente`: `SELECT` restrito ao próprio registro (`clientes.auth_user_id = auth.uid()`) e às próprias OSs/veículos vinculados (`ordens_servico.cliente_id = (SELECT id FROM clientes WHERE auth_user_id = auth.uid())` ou equivalente via função auxiliar) — preservando NFR12 (cliente só acessa suas próprias OSs e veículos) e a política já esboçada em `docs/architecture/supabase-persistence-model.md` §3 (ainda que com sintaxe `user_metadata` desatualizada — reescrever usando `papel_usuario()`/`auth.uid()`).
7. O botão/fluxo de logout do portal do cliente encerra a sessão real do Supabase Auth (`supabase.auth.signOut()`), não apenas a chave local `dev_oficina_cliente_ativo`.
8. Teste automatizado cobre: acesso anônimo a `/cliente/*` continua bloqueado (regressão do teste já existente da Story 1.1/Fase 0 de segurança), acesso com sessão de cliente real é liberado, tentativa de um cliente autenticado ler dados de outro cliente é bloqueada pelo RLS.
9. Par mobile do portal do cliente (`src/pages/cliente/mobile/`) verificado — o portal do cliente é majoritariamente mobile-first (FR19), então esta verificação é particularmente relevante.
10. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### O bypass real, confirmado no código
`ProtectedRoute.jsx` (bloco `portal === 'cliente'`):
```js
let clienteSalvo = null
try {
  clienteSalvo = localStorage.getItem('dev_oficina_cliente_ativo')
} catch {}
if (!clienteSalvo) {
  return <Navigate to={`/cliente/entrar?returnUrl=${returnUrl}`} replace />
}
return children
```
Isso verifica apenas a **presença** da chave, não sua validade contra nenhum backend — qualquer pessoa pode abrir o devtools, rodar `localStorage.setItem('dev_oficina_cliente_ativo', 'qualquer-coisa')` e acessar `/cliente/*`. A Story 1.1 (Epic 1) já eliminou o *fallback mock* de cliente anônimo (Risco R-15, `ClienteContext.jsx` linha 19-20 antiga removida), mas não substituiu a checagem por autenticação real — essa é exatamente a lacuna que esta story fecha, e é o motivo pelo qual esta story pertence ao Epic 2 (depende de `clientes` já estar em Supabase, Story 2.5) e não ao Epic 1.

### Padrão de referência: `funcionarios.auth_user_id`
O módulo de Funcionários (Story 1.10 + Fase 0 de segurança) já implementa exatamente este padrão para a equipe interna: `funcionarios.auth_user_id UUID`, provisionado via Edge Function `criar-login-funcionario`, com papel gravado em `app_metadata.role`. Esta story replica o mesmo padrão para clientes, adaptado ao fluxo de ativação via WhatsApp em vez de convite por e-mail direto do admin.

### Identificador de login do cliente — decisão em aberto
Nem todo cliente PF cadastrado no balcão necessariamente tem e-mail (campo `email` em `public.clientes` é opcional — `TEXT`, não `NOT NULL`). O Supabase Auth por padrão usa e-mail como identificador de login. Se a oficina cadastra clientes sem e-mail, será necessário: (a) exigir e-mail no cadastro de cliente que vai receber acesso ao portal (mudança de UX no formulário de cliente), ou (b) usar autenticação por telefone (Supabase Auth suporta login por SMS/telefone, mas exige provedor de SMS configurado, custo adicional). **Registrar como Open Question para `@architect`/`@po`** — não decidir unilateralmente nesta story sem validação de negócio.

### RLS de referência (a corrigir a sintaxe desatualizada)
`docs/architecture/supabase-persistence-model.md` §3 já esboça a intenção ("Cliente vê apenas suas OSs", `cliente_id = auth.uid()`), mas usa `auth.uid()` diretamente como se fosse igual ao `id` de `clientes` — isso só funciona se `clientes.id = auth.uid()` literalmente, o que não é o caso no schema real (`clientes.id TEXT`, gerado pelo padrão `cli-${timestamp}`, não um UUID de auth). A política real precisa de um `JOIN`/subquery via `auth_user_id`, não uma comparação direta — mais uma inconsistência entre o documento de arquitetura e o schema real a não seguir literalmente.

### Riscos
- Esta é, junto com a Story 2.17, uma das duas stories de maior superfície de segurança do Epic 2 — envolve dado pessoal de clientes (LGPD, NFR13) e é o portal historicamente mais vulnerável do sistema (Risco R-15 do PRD). Recomenda-se revisão dedicada do `@architect` e teste manual explícito de "cliente A não consegue ver dados do cliente B" antes de aprovar o gate.
- Não implementar nenhuma forma de "acesso de convidado"/fallback anônimo para o portal do cliente, mesmo temporariamente — isso reintroduziria exatamente o Risco R-15 que a Story 1.1 já mitigou parcialmente.
