## Story (histórico — não implementar)

**Como** cliente da oficina,
**Quero** ativar meu acesso ao portal `/cliente` através de um link de ativação enviado por WhatsApp e fazer login real com senha própria,
**Para que** apenas eu (e não qualquer visitante que abra o devtools) consiga ver minhas OSs e veículos — encerrando o contorno hoje existente na proteção do portal do cliente.

*(Premissa de "ativação via WhatsApp" substituída pelo fluxo de cadastro por CPF com aprovação da Secretaria — ver ADR-007. Preservado apenas para contexto histórico.)*

## Diagnóstico técnico preservado (ainda válido, reaproveitado pela Story 2.20c)

### O bypass real, confirmado no código
`ProtectedRoute.jsx` (bloco `portal === 'cliente'`):
```js
let clienteSalvo = null
try {
  clienteSalvo = localStorage.getItem('dev_oficina_cliente_ativo')
} catch {}
if (!clienteSalvo) {
  return <Navigate to={`/cliente/entrar?returnUrl=${returnUrl}`} replace />
}
return children
```
Isso verifica apenas a **presença** da chave, não sua validade contra nenhum backend — qualquer pessoa pode abrir o devtools, rodar `localStorage.setItem('dev_oficina_cliente_ativo', 'qualquer-coisa')` e acessar `/cliente/*`. Este diagnóstico permanece a motivação técnica da Story 2.20c, que substitui essa checagem por validação de sessão real do Supabase Auth com `app_metadata.role === 'cliente'`.

### Padrão de referência: `funcionarios.auth_user_id`
O módulo de Funcionários já implementa o padrão de `auth_user_id` + papel em `app_metadata` para a equipe interna. A Story 2.20a replica um padrão análogo para clientes (`clientes.auth_user_id`), mas com a Edge Function `cliente-auth` (ADR-007), não com convite direto do admin.
