# Story 2.9: Migração de Compras (Pedidos) e Cotações para Supabase Postgres

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** C — Suprimentos
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @data-engineer
**Dependências:** Story 2.7 (Terceiros/fornecedores), Story 2.8 (Estoque — recebimento de pedido dá entrada em estoque)

---

## Story

**Como** administrador ou secretária que negocia compras de peças com fornecedores,
**Quero** que Pedidos de Compra e Cotações de peças sejam persistidos em Supabase Postgres,
**Para que** o histórico de compras e o fluxo de cotação com fornecedores externos (incluindo o portal público `/cotacao/:id`) fiquem consistentes e compartilhados entre todos os usuários da oficina.

---

## Acceptance Criteria

1. `src/repositories/comprasRepository.js` (71 linhas) passa a ler/gravar em `public.compras_pedidos` e `public.compras_cotacoes` via Supabase quando configurado, com fallback local, preservando todas as assinaturas atuais: `carregarCompras`, `obterCompraPorId`, `salvarCompra`, `excluirCompra`, `receberCompraNoEstoque`, `buscarCotacoes`, `obterCotacaoPorId`, `salvarCotacaoAutodepecas`, `excluirCotacaoAutodepecas`, `buscarCotacaoPorOS`, `aprovarCotacaoEGerarPedidoCompra`.
2. Mapeamento de campos para `compras_pedidos`: `numero_pedido` (`UNIQUE`), `fornecedor_id` (FK para `terceiros`), `status` (`CHECK IN ('pendente','aprovado','entregue','cancelado')`), `itens` (JSONB, não convertido campo a campo), `valor_total`, `data_previsao_entrega`.
3. Mapeamento de campos para `compras_cotacoes`: `numero_cotacao` (`UNIQUE`), `ordem_servico_ref`, `status` (`CHECK IN ('em_cotacao','respondida','aprovada','cancelada')`), `itens` (JSONB), `propostas_fornecedores` (JSONB).
4. `receberCompraNoEstoque()` continua orquestrando, na sequência atual, a atualização de status do pedido para `entregue` e o registro de entrada correspondente via `estoqueRepository.registrarMovimentacao()` (Story 2.8) — nenhuma mudança de fluxo de negócio, apenas troca da fonte de persistência.
5. `aprovarCotacaoEGerarPedidoCompra()` continua criando um novo `compras_pedidos` a partir de uma cotação aprovada, preservando a referência `ordem_servico_ref` quando a cotação estiver vinculada a uma OS.
6. RLS de `public.compras_pedidos` e `public.compras_cotacoes` usa `public.papel_usuario()`: hoje só existem políticas `"Admin total compras_pedidos"` e `"Admin total compras_cotacoes"` (`FOR ALL`, admin, desde a migration `20260924130000`). Esta story cria migration incremental adicionando `SELECT`/`INSERT`/`UPDATE` para `secretaria` (fluxo de compras é operação de balcão, não exclusiva do admin) — decisão a confirmar com `@po`, default seguro caso não haja resposta: manter admin-only e documentar a limitação.
7. O acesso da rota pública `/cotacao/:id` (`CotacaoAutoPecaPage.jsx`, fornecedor externo respondendo a uma cotação) é resolvido por **token de acesso via RPC** — **não** por leitura direta da tabela `compras_cotacoes` para o papel `anon` (ver Story 2.17, que implementa o padrão genérico de aprovação pública por token). Esta story apenas garante que `compras_cotacoes` **não** ganha nenhuma política `TO anon` — o consumo pela página pública é responsabilidade da Story 2.17.
8. Teste automatizado cobre CRUD de pedidos e cotações com Supabase mockado, fallback local, e o fluxo `aprovarCotacaoEGerarPedidoCompra`.
9. Par mobile (`src/pages/dashboard/suprimentos/mobile/MobileComprasPage.jsx`) verificado.
10. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/repositories/comprasRepository.js` delega para funções em `src/constants/comprasData.js` (458 linhas — nota: `docs/brownfield-architecture.md` registra 699 linhas; a redução reflete a remoção de dados mock no commit `e7ef8a4`, documento de brownfield desatualizado neste ponto).

### Tabelas-alvo
`public.compras_pedidos` e `public.compras_cotacoes` (migration `20260921_initial_schema.sql` §8). Ambas já têm RLS `admin`-only desde a Fase 0 de segurança.

### Fluxo público de cotação (`CotacaoAutoPecaPage.jsx`, rota `/cotacao/:id`)
`docs/brownfield-architecture.md` (§Módulos-chave) documenta esse fluxo como "portal público via link" — hoje, sem backend real, a página provavelmente lê a cotação inteira do `localStorage` ou de um formato compartilhado por URL. No Supabase, **nunca** expor `compras_cotacoes` para `anon`; o padrão correto (Story 2.17) é uma função `RPC SECURITY DEFINER` que recebe um token opaco (não o `id` sequencial) e retorna apenas os campos necessários para o fornecedor responder. Esta story **não implementa** esse RPC — apenas não deve introduzir nenhuma política `anon` como atalho de curto prazo.

### RLS já existente
`"Admin total compras_pedidos"` e `"Admin total compras_cotacoes"` — `FOR ALL`, admin. Sem política de leitura/escrita para secretaria — gap a resolver conforme AC6.

### Dependências
- Depende de Story 2.7 (fornecedor/`terceiros`) e Story 2.8 (`estoqueRepository.registrarMovimentacao`).
- Story 2.17 depende desta (a tabela `compras_cotacoes` precisa existir migrada para o RPC de token funcionar sobre dados reais).

### Arquivos afetados
- **[MODIFY]** `src/repositories/comprasRepository.js`
