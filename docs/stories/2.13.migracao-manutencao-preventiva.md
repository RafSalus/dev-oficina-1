# Story 2.13: Migração de Manutenção Preventiva para Supabase Postgres (Nova Tabela)

## Story

**Como** administrador ou secretária que acompanha a "ficha de saúde" dos veículos da carteira de clientes,
**Quero** que os registros de manutenção preventiva (itens do catálogo preventivo e execuções) sejam persistidos em Supabase Postgres, com a atualização de quilometragem restrita a uma RPC dedicada,
**Para que** o cálculo de saúde do veículo (`calcularSaudeVeiculo()`) use dados reais e atualizados, compartilhados entre todos os usuários, sem que este módulo grave diretamente em colunas de `veiculos` além do estritamente necessário.

---

## Escopo

**Dentro do escopo (IN):**
- Tabela `manutencoes_preventivas`.
- Decisão documentada sobre o catálogo de itens preventivos (tabela vs. constante).
- RPC restrita para atualização de `veiculos.km_atual`.

**Fora do escopo (OUT):**
- Nova fórmula de cálculo de saúde do veículo — `calcularSaudeVeiculo()` é preservada como está.
- Qualquer UI de edição do catálogo de itens preventivos, caso a decisão seja mantê-lo como tabela — a tela de administração desse catálogo (se necessária) é item de backlog, não desta story.

## Acceptance Criteria

1. É criada a tabela `public.manutencoes_preventivas` (nova), com `id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text` (ADR-005 §2.6), cobrindo os campos manipulados por `src/constants/mockManutencaoPreventiva.js` para registros de execução (`registrarExecucaoPreventiva()`), com FK para `public.veiculos(id)`.
2. O catálogo de itens preventivos (`ITENS_PREVENTIVOS_CATALOGO`) é avaliado quanto à necessidade de virar tabela própria (`public.itens_preventivos_catalogo`) ou permanecer como constante estática em código — decisão do `@data-engineer`: se o catálogo for editável pelo admin na UI, deve virar tabela; se for fixo e só alterado por deploy de código, permanece constante. **Decisão documentada nesta rodada: manter como constante estática em código nesta story**, por não haver hoje nenhuma tela de edição desse catálogo pela UI — se o `@po` priorizar uma tela de administração do catálogo no futuro, essa mudança de schema é tratada em story própria, não retroativamente nesta.
3. As funções puras de cálculo de data (`converterDataParaDate`, `adicionarMesesAData`, `calcularDiasRestantes`) **permanecem** em `mockManutencaoPreventiva.js` (ou são movidas para `src/utils/`, seguindo o padrão de extração de utilitários já aplicado na Story 1.11) — não dependem de acesso a dados e não precisam de mudança de assinatura.
4. É criado `src/repositories/manutencaoPreventivaRepository.js` (novo), expondo assíncronamente: `carregarManutencoesPreventivas()`, `carregarVeiculosAtivosPreventiva()` (delegando para `veiculosRepository`, Story 2.6, em vez de `carregarTodosVeiculosDaFrota()` diretamente), `registrarExecucaoPreventiva(dados)`, `atualizarHodometroVeiculo(placa, novoKm)` — usando o wrapper fail-closed da Story 2.1, sem fallback em falha.
5. `calcularSaudeVeiculo(veiculo, todasPreventivas)` permanece uma função pura que recebe os dados já carregados como parâmetro — o repositório é responsável por buscar `todasPreventivas` antes de chamar essa função; a lógica de cálculo de saúde em si não é alterada (não inventar nova fórmula).
6. `atualizarHodometroVeiculo()` passa a gravar em `public.veiculos.km_atual` através de uma **RPC restrita** `public.atualizar_hodometro_veiculo(placa TEXT, novo_km INTEGER)` (ADR-005 §2.13) — não por um `UPDATE` genérico em `veiculos`, porque **o mecânico não tem `UPDATE` em `veiculos`** (Story 2.6, RLS: `mecanico` só tem `SELECT`) e este módulo é operado também pelo mecânico. A RPC (`SECURITY DEFINER`, `SET search_path = ''`) só altera a coluna `km_atual`, valida que o novo valor não é menor que o atual (evitar regressão de hodômetro por erro de digitação, salvo confirmação explícita — a critério do `@dev`) e elimina a fonte potencial de divergência de quilometragem entre este módulo e o cadastro de veículos.
7. RLS de `public.manutencoes_preventivas` usa `public.papel_usuario()`: `admin` acesso total; `secretaria`/`mecanico` `SELECT`/`INSERT` (registrar execução de preventiva é operação de balcão/oficina); `UPDATE`/`DELETE` restritos ao `admin`.
8. Triggers de auditoria e `updated_at` (Story 2.2) anexadas à nova tabela.
9. Teste automatizado cobre: registro de execução preventiva, cálculo de saúde do veículo com dados mockados, atualização de hodômetro via RPC refletindo em `veiculos.km_atual` (incluindo o caso de `mecanico` autenticado, sem `UPDATE` direto na tabela).
10. Par mobile (`src/pages/dashboard/manutencao-preventiva/mobile/MobileManutencaoPreventivaPage.jsx`) verificado.
11. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/constants/mockManutencaoPreventiva.js` (324 linhas — brownfield doc registra 698, redução após limpeza de mocks). Depende de `carregarTodosVeiculosDaFrota()` (`src/constants/mockClientesVeiculos.js`) — **esta dependência é resolvida pela Story 2.6**, que cria `veiculosRepository.js`; esta story (2.13) deve consumir esse repositório, não o módulo de constants legado.

### Por que uma RPC e não um `UPDATE` direto (ADR-005 §2.13)
`veiculos` concede `UPDATE` apenas a `admin` e `secretaria` (Story 2.6). O mecânico, que também opera a manutenção preventiva em campo, não tem esse privilégio. Uma RPC `SECURITY DEFINER` restrita a alterar somente `km_atual` resolve isso sem abrir `UPDATE` completo de `veiculos` para o mecânico — segue o princípio de menor privilégio (NFR12).

### Duplicação de quilometragem — problema real a corrigir
`atualizarHodometroVeiculo(placa, novoKm)` hoje provavelmente atualiza o km em uma estrutura própria deste módulo (a confirmar lendo a função completa, linha 258), separada do `km_atual` gravado em `public.veiculos` (Story 2.6). Esta story elimina essa duplicação, gravando sempre em `veiculos.km_atual` via a RPC do AC6, para que a Agenda, o cadastro de veículos e a ficha de saúde preventiva nunca divirjam sobre a quilometragem atual de um carro.

### `calcularSaudeVeiculo()` — não inventar nova regra
Esta é a função central do módulo (120-258 do arquivo atual, a maior função do arquivo). Não reimplementar do zero — apenas garantir que ela continue recebendo os mesmos formatos de dado que recebia antes (agora vindos do Postgres em vez do `localStorage`), preservando 100% do resultado observável.

### Riscos
- Manter o catálogo de itens preventivos como constante (decisão desta rodada) pode precisar ser revertida se o `@po` priorizar edição via UI — nesse caso, a migração para tabela é um trabalho novo, não uma simples reversão; registrar essa possibilidade no backlog.
- A RPC de hodômetro precisa validar corretamente o caso de regressão de quilometragem (erro de digitação vs. troca de veículo/reset legítimo) — uma validação rígida demais bloquearia um caso de uso real; uma validação frouxa demais permitiria dado inconsistente.
- Qualquer tela ou script administrativo que hoje grave `km_atual` diretamente em `veiculos` (fora desta RPC) precisa ser identificado e migrado para não criar dois caminhos de escrita divergentes.
