# Story 2.17: Acesso Público Seguro por Token para Cotação, Aprovação, Orçamento e Vistoria

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** E — Ordem de Serviço Completa
**Autor:** River (@sm)
**Executor:** @data-engineer
**Quality Gate:** @architect
**Dependências:** Story 2.9 (Compras e Cotações), Story 2.14 (OS)

## Story

**Como** cliente ou fornecedor externo que recebe um link de `/cotacao/:id`, `/aprovacao/:id`, `/orcamento/:id` ou `/vistoria/:id`,
**Quero** conseguir visualizar e responder ao conteúdo do link sem precisar de login,
**Para que** o fluxo comercial (aprovação de orçamento, resposta de cotação, visualização de checklist de vistoria) funcione como hoje — mas **sem** o sistema expor as tabelas de domínio (`ordens_servico`, `compras_cotacoes`, `clientes`) diretamente para o papel `anon` do Supabase, o que vazaria dados de todos os clientes/OSs para qualquer portador da chave pública (anon key).

---

## Acceptance Criteria

1. É criado um padrão genérico de **token de acesso público**: uma coluna `token_publico TEXT UNIQUE` (ou tabela auxiliar dedicada `public.tokens_acesso_publico`, a critério do `@data-engineer` — ver Dev Notes para trade-offs) contendo um valor aleatório opaco (gerado com `gen_random_uuid()` ou `encode(gen_random_bytes(24), 'base64')`), gerado no momento em que a OS/cotação é criada ou passa a precisar de acesso externo, com **data de expiração** (`expira_em TIMESTAMPTZ`).
2. É criada uma função `RPC` `SECURITY DEFINER` por fluxo público — no mínimo `public.obter_aprovacao_por_token(token TEXT)`, `public.obter_cotacao_por_token(token TEXT)`, `public.obter_vistoria_por_token(token TEXT)` — que: (a) valida o token contra a coluna/tabela de tokens, (b) confirma que não expirou, (c) retorna **apenas os campos necessários** para a tela pública renderizar (nunca `SELECT *`), (d) nunca aceita o `id` sequencial/UUID da tabela diretamente como parâmetro de busca pública.
3. **Nenhuma política de RLS `TO anon` é criada diretamente sobre `ordens_servico`, `compras_cotacoes` ou `clientes`** — o único caminho de leitura anônima é através das funções RPC do AC2, que rodam com privilégio elevado (`SECURITY DEFINER`) mas aplicam sua própria lógica de validação de token, não a política de RLS da tabela.
4. As URLs geradas para o cliente/fornecedor (ex.: em `wa.me` ou impressão) passam a usar o `token_publico` em vez do `id` sequencial da OS/cotação como parâmetro de rota (`/aprovacao/:token` em vez de `/aprovacao/:id`) — **atenção:** isso é uma mudança de contrato de URL; qualquer link já enviado a um cliente antes desta story deixa de funcionar. Avaliar com `@po`/`@architect` uma janela de transição (aceitar tanto `id` legado quanto `token` novo por um período, ou aceitar a quebra pontual dado que o sistema ainda não está em produção real com clientes).
5. A rota de aprovação de orçamento (`AprovacaoOrcamentoClientePage.jsx`) grava a decisão do cliente (aprovar/recusar item) através de uma segunda função `RPC SECURITY DEFINER` (`public.registrar_decisao_aprovacao(token TEXT, decisao JSONB)`), nunca por `UPDATE` direto na tabela via `anon`.
6. Teste automatizado (mock de `supabase.rpc()`) cobre: token válido retorna dados, token expirado é rejeitado, token inexistente é rejeitado, chamada às tabelas de domínio diretamente como `anon` continua bloqueada pelo RLS padrão (`authenticated`-only).
7. As 9 rotas públicas por design da FR3 (`/`, `/cliente/entrar`, `/gestao/entrar`, `/gestao/recuperar-senha`, `/gestao/acesso-negado`, `/cotacao/:id`, `/aprovacao/:id`, `/orcamento/:id`, `/vistoria/:id`) continuam **acessíveis e funcionais** após esta story — o Risco R-1 do PRD (guard de rota derrubar rotas públicas) permanece mitigado; esta story não altera o guard de rota (`ProtectedRoute`), apenas a fonte de dados por trás das páginas.
8. `npm run lint` e `npm test` sem novos erros; nenhum arquivo `.sql`/`.js` excede 400 linhas.

## Dev Notes

### Por que esta story é necessária (não é uma antecipação de OQ-3)
Esta story **não** resolve OQ-3 (restrição de rede da oficina — isso é uma pendência arquitetural separada, fora do Epic 2, aguardando ADR do `@architect`, PRD §4.6). O problema aqui é mais simples e já tem solução padrão em arquiteturas Supabase: **como servir dados a um visitante anônimo sem abrir a tabela inteira para `anon`.** A resposta padrão é RPC com token opaco, não RLS `TO anon` na tabela (que foi, inclusive, o padrão inseguro removido na Fase 0 de segurança — a migration original tinha `"Public anon select funcionarios"` etc., removidas por vazarem dados).

### Trade-off: coluna de token vs. tabela dedicada
- **Coluna `token_publico` direto em `ordens_servico`/`compras_cotacoes`:** mais simples, mas mistura uma preocupação de segurança/acesso com a tabela de domínio; token fica visível para qualquer `SELECT` autenticado na tabela (não é segredo para a equipe interna, então talvez seja aceitável).
- **Tabela dedicada `public.tokens_acesso_publico (token, tabela_referencia, registro_id, expira_em, usado_em)`:** mais flexível (um único padrão para todos os fluxos públicos), mais fácil de expirar/revogar em lote, mas exige um `JOIN`/lookup extra em cada RPC.
O `@data-engineer` decide com base na complexidade real dos 3-4 fluxos públicos existentes; qualquer uma das duas abordagens satisfaz os ACs desta story, desde que a tabela de domínio nunca seja exposta a `anon` diretamente.

### Fluxos públicos reais a cobrir (confirmados em `src/App.jsx`)
- `/cotacao/:id` → `CotacaoAutoPecaPage.jsx` (fornecedor externo responde cotação de peça).
- `/aprovacao/:id` e `/orcamento/:id` → ambos apontam para `AprovacaoOrcamentoClientePage.jsx` (mesma página, duas rotas — preservar esse comportamento).
- `/vistoria/:id` → `VistoriaEntradaClientePage.jsx` (cliente visualiza checklist/fotos de entrada do veículo).

### Risco de quebra de link já enviado (AC4)
Como o sistema ainda não está em operação real com clientes (Epic 1/2 em desenvolvimento), o risco de "link antigo quebrado" é teoricamente baixo, mas deve ser confirmado com o `@po`/proprietário antes de decidir não implementar um período de transição — não assumir unilateralmente que não há impacto.

### Arquivos afetados
- **[NEW]** `supabase/migrations/{timestamp}_tokens_acesso_publico.sql`
- **[MODIFY]** `src/pages/CotacaoAutoPecaPage.jsx`
- **[MODIFY]** `src/pages/AprovacaoOrcamentoClientePage.jsx`
- **[MODIFY]** `src/pages/VistoriaEntradaClientePage.jsx`
- **[NEW]** `tests/unit/tokensAcessoPublico.test.js`

### Riscos
- Este é o ponto de maior superfície de ataque do sistema (única leitura de dados sem autenticação) — qualquer bug na validação de expiração ou no filtro de campos do RPC vaza dados para a internet pública. Recomenda-se revisão dedicada do `@architect` (Quality Gate desta story) e, se possível, teste de penetração manual leve (tentar token adulterado, token de outra OS, token expirado) antes de fechar a story.
