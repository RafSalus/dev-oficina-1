# Story 2.5: Migração de Clientes para Supabase Postgres

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** B — Cadastros
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @data-engineer
**Dependências:** Story 2.1, Story 2.2 (auditoria/`updated_at` — `clientes` está na lista de tabelas auditadas)

---

## Story

**Como** secretária ou administrador da oficina,
**Quero** que o cadastro de Clientes seja persistido em Supabase Postgres com controle de acesso por perfil e sem fallback local em caso de falha,
**Para que** os dados de clientes (LGPD-sensíveis: CPF/CNPJ, telefone, e-mail, endereço) sobrevivam a troca de navegador/dispositivo, sejam compartilhados entre todos os usuários da oficina e parem de ficar em texto claro no `localStorage` de qualquer navegador que abra a URL (Risco R-13 do PRD), sem nunca produzir um "sucesso falso" (ADR-005).

---

## Escopo

**Dentro do escopo (IN):**
- Migração de `clientesRepository.js` para Supabase com wrapper fail-closed da Story 2.1.
- ID gerado pelo banco (`gen_random_uuid()::text`), não mais pelo front.
- Validação/ajuste de RLS de `public.clientes`.
- Exclusão de cliente restrita ao admin.

**Fora do escopo (OUT):**
- Vínculo `auth_user_id` em `clientes` e qualquer coisa relacionada a cadastro/login do cliente — isso pertence à Story 2.20a (ADR-007), não a esta story.
- Tratamento de cadastros pendentes de aprovação (FR24) — também 2.20a/2.20b.
- Migração de `veiculos` (Story 2.6, que depende desta).

---

## Acceptance Criteria

1. `src/repositories/clientesRepository.js` passa a ler e gravar em `public.clientes` via Supabase quando `isSupabaseConfigured` for verdadeiro, usando os helpers e o wrapper fail-closed da Story 2.1 (ADR-005 §2.1–§2.2) — **sem fallback local em caso de falha de chamada**; o modo local (dev/teste, Supabase não configurado) continua disponível conforme a política da Story 2.1.
2. Todas as funções públicas hoje exportadas (`carregarClientes`, `obterClientePorId`, `buscarClientePorDocumento`, `salvarCliente`, `excluirCliente`, `obterVeiculosDoCliente`) mantêm exatamente a mesma assinatura e formato de retorno (incluindo os campos `value`/`id` duplicados por compatibilidade histórica com `react-select`, conforme uso atual em `clientesRepository.js:66-90`) — nenhuma tela consumidora precisa mudar.
3. O mapeamento de campos JS↔banco cobre: `nome`, `tipo` (`PF`/`PJ`), `cpf_cnpj`/`cpfCnpj` (ou `documento`, conforme nomenclatura em uso na UI — documentar a divergência real encontrada entre `constants/mockClientesVeiculos.js` e a coluna `cpf_cnpj` da tabela), `telefone`, `telefone_secundario`, `email`, `endereco` (JSONB, não convertido campo a campo), `observacoes`.
4. `buscarClientePorDocumento()` usa filtro no servidor (`supabase.from('clientes').select().eq(...)` ou `.filter()` com normalização de dígitos) em vez de trazer toda a tabela para filtrar no cliente, respeitando NFR9 (leitura ≤ 1s no 4G).
5. RLS de `public.clientes` é validada/ajustada usando exclusivamente `public.papel_usuario()`: `admin` tem acesso total (já existe); `secretaria` pode `SELECT`, `INSERT` e `UPDATE` (já existe desde a migration `20260924130000`); `mecanico` tem apenas `SELECT` (política de leitura de equipe já existente, `"Equipe le clientes"`, cobre `secretaria` e `mecanico`); nenhuma política concede acesso anônimo. **Exclusão de cliente (`DELETE`) permanece exclusiva do `admin`** (não há política de `DELETE` para `secretaria` — decisão confirmada nesta rodada, dado o impacto de `ON DELETE CASCADE` em `veiculos`/`ordens_servico`; ver Dev Notes).
6. `salvarCliente()` **não gera mais o `id` no front** (`cli-${timestamp}`) — a coluna `id` passa a ter `DEFAULT gen_random_uuid()::text` (ADR-005 §2.6) e o `INSERT` retorna a linha criada via `.select().single()`. IDs legados com o prefixo `cli-` continuam válidos para leitura (coluna é `TEXT`).
7. Teste automatizado (Vitest, mock de `supabase-js`) cobre: leitura com Supabase configurado, comportamento fail-closed quando indisponível (erro explícito, sem fallback), busca por documento normalizando máscara (pontos/traço/barra removidos antes de comparar), e criação confirmando que o `id` retornado vem do banco (não gerado no cliente).
8. Tela desktop `src/pages/dashboard/clientes/` (ou caminho real do módulo de Clientes) e o par mobile `src/pages/dashboard/clientes/mobile/MobileClientesPage.jsx` são verificados manualmente ou via teste de integração leve: ambos continuam funcionando sem alteração de código, consumindo o mesmo repositório (Single Logic Adaptive UI, ADR-004) — nenhuma nova duplicação é criada.
9. Triggers de auditoria e `updated_at` (Story 2.2) confirmadas ativas em `clientes`.
10. `npm run lint` e `npm test` sem novos erros; arquivos modificados permanecem ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/repositories/clientesRepository.js` (113 linhas) lê/grava `MOCK_CLIENTES_VEICULOS` (`src/constants/mockClientesVeiculos.js`, 397 linhas segundo `docs/brownfield-architecture.md`) via `localStorage` (`STORAGE_KEY_CLIENTES = 'dev_oficina_clientes'`). Os objetos usam `value` **e** `id` como o mesmo identificador — padrão herdado de uso direto em `react-select`, preservar por compatibilidade (não normalizar para um único campo nesta story, para não quebrar todos os consumidores).

### Tabela-alvo
`public.clientes` (migration `20260921_initial_schema.sql` §2): `id TEXT PRIMARY KEY DEFAULT gen_random_uuid()::text` (ADR-005 §2.6 — ajuste de `DEFAULT` a aplicar nesta story se ainda não existir), `nome TEXT`, `tipo TEXT CHECK IN ('PF','PJ')`, `cpf_cnpj TEXT UNIQUE`, `telefone TEXT`, `telefone_secundario TEXT`, `email TEXT`, `endereco JSONB`, `observacoes TEXT`, `created_at`, `updated_at` (trigger da Story 2.2).

### RLS já existente (migration `20260924130000_rls_papel_app_metadata.sql`)
- `"Admin total clientes"` — `FOR ALL`, `papel_usuario() = 'admin'`.
- `"Equipe le clientes"` — `FOR SELECT`, `papel_usuario() IN ('secretaria','mecanico')`.
- `"Secretaria grava clientes"` — `FOR INSERT`, `papel_usuario() = 'secretaria'`.
- `"Secretaria atualiza clientes"` — `FOR UPDATE`, `papel_usuario() = 'secretaria'`.
- **Decisão confirmada (não é mais gap aberto):** exclusão de cliente é exclusiva do `admin` (via `FOR ALL`), dado o impacto de `ON DELETE CASCADE` em `veiculos` (ver Story 2.6, alerta de cascata). Não criar política de `DELETE` para `secretaria`.

### Vínculo com autenticação de cliente — fora do escopo desta story
A coluna `clientes.auth_user_id` e qualquer lógica de cadastro/aprovação de cliente (FR17/FR18/FR24) pertencem à Story 2.20a (ADR-007), que depende desta story. Não antecipar esse schema aqui.

### Dependência para a Story 2.6 (Veículos)
A Story 2.6 depende desta por causa da FK `veiculos.cliente_id REFERENCES clientes(id)`. `obterVeiculosDoCliente()` nesta story ainda lê o array `veiculos` embutido no objeto de cliente local (padrão legado); a Story 2.6 é responsável por migrar essa função para consultar a tabela `veiculos` real via `cliente_id`. **Alerta de `ON DELETE CASCADE`:** excluir um cliente no banco real excluirá silenciosamente todos os seus veículos — comportamento diferente do `localStorage` atual; documentado também na Story 2.6.

### Arquivos afetados
- **[MODIFY]** `src/repositories/clientesRepository.js`
- **[NEW]** `tests/unit/clientesRepository.test.js`
- Nenhuma tela de UI deve precisar de alteração (ADR-002).

### Riscos
- `cpf_cnpj UNIQUE` no banco pode rejeitar duplicatas que hoje passam silenciosamente no `localStorage` — tratar com `ErroRepositorio` código `DUPLICADO` (Story 2.1) e mensagem amigável ("CPF/CNPJ já cadastrado") em vez de deixar o erro do Postgres vazar para o usuário.
- Migrar de "ID gerado no front" para "ID gerado no banco" exige que nenhum código dependa do formato `cli-${timestamp}` para lógica (apenas para exibição, se houver) — auditar antes de remover a geração local.
