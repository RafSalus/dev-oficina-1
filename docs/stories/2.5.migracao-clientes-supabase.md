# Story 2.5: Migração de Clientes para Supabase Postgres

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** B — Cadastros
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @data-engineer

---

## Story

**Como** secretária ou administrador da oficina,
**Quero** que o cadastro de Clientes seja persistido em Supabase Postgres com controle de acesso por perfil,
**Para que** os dados de clientes (LGPD-sensíveis: CPF/CNPJ, telefone, e-mail, endereço) sobrevivam a troca de navegador/dispositivo, sejam compartilhados entre todos os usuários da oficina e parem de ficar em texto claro no `localStorage` de qualquer navegador que abra a URL (Risco R-13 do PRD).

---

## Acceptance Criteria

1. `src/repositories/clientesRepository.js` passa a ler e gravar em `public.clientes` via Supabase quando `isSupabaseConfigured` for verdadeiro, usando os helpers da Story 2.1 (mapeamento de campos, wrapper de erro) e preservando fallback para `localStorage` quando offline/não configurado.
2. Todas as funções públicas hoje exportadas (`carregarClientes`, `obterClientePorId`, `buscarClientePorDocumento`, `salvarCliente`, `excluirCliente`, `obterVeiculosDoCliente`) mantêm exatamente a mesma assinatura e formato de retorno (incluindo os campos `value`/`id` duplicados por compatibilidade histórica com `react-select`, conforme uso atual em `clientesRepository.js:66-90`) — nenhuma tela consumidora precisa mudar.
3. O mapeamento de campos JS↔banco cobre: `nome`, `tipo` (`PF`/`PJ`), `cpf_cnpj`/`cpfCnpj` (ou `documento`, conforme nomenclatura em uso na UI — documentar a divergência real encontrada entre `constants/mockClientesVeiculos.js` e a coluna `cpf_cnpj` da tabela), `telefone`, `telefone_secundario`, `email`, `endereco` (JSONB, não convertido campo a campo), `observacoes`.
4. `buscarClientePorDocumento()` usa filtro no servidor (`supabase.from('clientes').select().eq(...)` ou `.filter()` com normalização de dígitos) em vez de trazer toda a tabela para filtrar no cliente, respeitando NFR9 (leitura ≤ 1s no 4G).
5. RLS de `public.clientes` é validada/ajustada usando exclusivamente `public.papel_usuario()`: `admin` tem acesso total (já existe); `secretaria` pode `SELECT`, `INSERT` e `UPDATE` (já existe desde a migration `20260924130000`); `mecanico` tem apenas `SELECT` (política de leitura de equipe já existente, `"Equipe le clientes"`, cobre `secretaria` e `mecanico`); nenhuma política concede acesso anônimo.
6. Teste automatizado (Vitest, mock de `supabase-js`) cobre: leitura com Supabase configurado, fallback local quando indisponível, busca por documento normalizando máscara (pontos/traço/barra removidos antes de comparar), e criação com geração de `id` compatível com o padrão `cli-${timestamp}` hoje usado.
7. Tela desktop `src/pages/dashboard/clientes/` (ou caminho real do módulo de Clientes) e o par mobile `src/pages/dashboard/clientes/mobile/MobileClientesPage.jsx` são verificados manualmente ou via teste de integração leve: ambos continuam funcionando sem alteração de código, consumindo o mesmo repositório (Single Logic Adaptive UI, ADR-004) — nenhuma nova duplicação é criada.
8. `npm run lint` e `npm test` sem novos erros; arquivos modificados permanecem ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/repositories/clientesRepository.js` (113 linhas) lê/grava `MOCK_CLIENTES_VEICULOS` (`src/constants/mockClientesVeiculos.js`, 397 linhas segundo `docs/brownfield-architecture.md`) via `localStorage` (`STORAGE_KEY_CLIENTES = 'dev_oficina_clientes'`). Os objetos usam `value` **e** `id` como o mesmo identificador — padrão herdado de uso direto em `react-select`, preservar por compatibilidade (não normalizar para um único campo nesta story, para não quebrar todos os consumidores).

### Tabela-alvo
`public.clientes` (migration `20260921_initial_schema.sql` §2): `id TEXT PRIMARY KEY`, `nome TEXT`, `tipo TEXT CHECK IN ('PF','PJ')`, `cpf_cnpj TEXT UNIQUE`, `telefone TEXT`, `telefone_secundario TEXT`, `email TEXT`, `endereco JSONB`, `observacoes TEXT`, `created_at`, `updated_at` (trigger de `updated_at` vem da Story 2.2 — se 2.2 ainda não estiver implementada quando esta story rodar, o código de aplicação deve continuar gravando `dataAtualizacao` manualmente, sem depender do trigger).

### RLS já existente (migration `20260924130000_rls_papel_app_metadata.sql`)
- `"Admin total clientes"` — `FOR ALL`, `papel_usuario() = 'admin'`.
- `"Equipe le clientes"` — `FOR SELECT`, `papel_usuario() IN ('secretaria','mecanico')`.
- `"Secretaria grava clientes"` — `FOR INSERT`, `papel_usuario() = 'secretaria'`.
- `"Secretaria atualiza clientes"` — `FOR UPDATE`, `papel_usuario() = 'secretaria'`.
- **Gap identificado:** não há política de `DELETE` explícita para `secretaria` — apenas `admin` (via `FOR ALL`) pode excluir. Confirmar com `@po`/`@data-engineer` se isso é intencional (provavelmente sim, dado o impacto de excluir um cliente com veículos/OS vinculados) antes de decidir se `excluirCliente()` deve, na prática, apenas ser exposto na UI para o perfil admin.

### Dependência para a Story 2.6 (Veículos)
A Story 2.6 depende desta por causa da FK `veiculos.cliente_id REFERENCES clientes(id)`. `obterVeiculosDoCliente()` nesta story ainda lê o array `veiculos` embutido no objeto de cliente local (padrão legado); a Story 2.6 é responsável por migrar essa função para consultar a tabela `veiculos` real via `cliente_id`.

### Arquivos afetados
- **[MODIFY]** `src/repositories/clientesRepository.js`
- **[NEW]** `tests/unit/clientesRepository.test.js`
- Nenhuma tela de UI deve precisar de alteração (ADR-002).

### Riscos
- `cpf_cnpj UNIQUE` no banco pode rejeitar duplicatas que hoje passam silenciosamente no `localStorage` — decidir tratamento de erro amigável (toast `sonner` "CPF/CNPJ já cadastrado") em vez de deixar o erro do Postgres vazar para o usuário.
