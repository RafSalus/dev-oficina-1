# Story 2.8: Migração de Estoque e Movimentações (Kardex) para Supabase Postgres

**Status:** Draft
**Epic:** Epic 2 (Persistência Real Supabase Postgres & RLS)
**Onda:** C — Suprimentos
**Autor:** River (@sm)
**Executor:** @dev
**Quality Gate:** @data-engineer
**Dependências:** Story 2.7 (Peças)

## Story

**Como** administrador ou secretária responsável pelo controle de estoque,
**Quero** que toda movimentação de entrada, saída e ajuste de peças seja registrada em `public.estoque_movimentacoes` no Postgres,
**Para que** o Kardex de cada peça seja auditável, consistente entre usuários simultâneos e não se perca ao trocar de navegador.

---

## Acceptance Criteria

1. `src/repositories/estoqueRepository.js` (78 linhas) passa a ler/gravar em `public.estoque_movimentacoes` via Supabase quando configurado, com fallback local, preservando as assinaturas: `carregarMovimentacoes()`, `registrarMovimentacao(mov)`, `obterKardexPeca(pecaId)`, `obterSaldoPeca(pecaId)`.
2. `registrarMovimentacao()` continua responsável por atualizar o saldo (`estoque_atual`) da peça correspondente via `suprimentosRepository.salvarPeca()` (Story 2.7) — mantendo o fluxo atual de duas escritas (movimentação + atualização de saldo). Documentar em Dev Notes o risco de inconsistência entre as duas escritas não-atômicas e a mitigação adotada (ver Dev Notes).
3. Mapeamento de campos cobre: `peca_id` (FK), `tipo` (`entrada`/`saida`/`ajuste`, `CHECK` já existente no banco), `quantidade`, `motivo`, `documento_ref`, `usuario`.
4. `usuario` passa a ser preenchido automaticamente a partir do usuário autenticado (nome ou e-mail da sessão Supabase) quando disponível, em vez do valor fixo `'Sistema'` hoje usado como default — sem quebrar o fallback local (`'Sistema'` continua sendo o default quando não há sessão, ex.: ambiente offline).
5. RLS de `public.estoque_movimentacoes` usa `public.papel_usuario()`: hoje só existe a política `"Admin total estoque"` (`FOR ALL`, admin). Esta story deve criar migration incremental adicionando `SELECT` para `secretaria`/`mecanico` (necessário para consultar Kardex) e `INSERT` para `secretaria` e `mecanico` (para registrar consumo de peças durante a OS — necessário pelas Ondas E e F, mas a política deve ser criada aqui, quando a tabela é efetivamente ligada ao Supabase pela primeira vez) — decisão de escopo de escrita por perfil a confirmar com `@po`/`@architect` antes de codar (default seguro: `secretaria` e `mecanico` podem `INSERT`, ninguém além do `admin` pode `UPDATE`/`DELETE`, preservando a natureza de Kardex append-only).
6. Teste automatizado cobre: registro de entrada/saída/ajuste com recálculo de saldo, leitura de Kardex por peça, fallback local.
7. Par mobile (`src/pages/dashboard/suprimentos/mobile/MobileEstoquePage.jsx`) verificado.
8. `npm run lint` e `npm test` sem novos erros; arquivos ≤ 400 linhas.

## Dev Notes

### Estado atual do código
`src/repositories/estoqueRepository.js` delega para `carregarMovimentacoesEstoque()`/`salvarMovimentacoesEstoque()` em `src/constants/cadastrosSuprimentosData.js`, e depende de `suprimentosRepository.obterPecaPorId()`/`salvarPeca()` (Story 2.7) para atualizar o saldo — este acoplamento entre repositórios já existe hoje e deve ser preservado.

### Consistência de duas escritas não-atômicas (AC2, risco a mitigar)
Hoje, `registrarMovimentacao()` faz duas operações sequenciais: (1) grava a movimentação, (2) lê e regrava a peça com o novo saldo. No Postgres, se a segunda escrita falhar após a primeira ter sucesso, o Kardex fica dessincronizado do saldo real. Duas mitigações possíveis, a critério do `@dev`/`@data-engineer`:
- **Opção simples (aceitável para o MVP):** manter as duas escritas sequenciais como hoje, mas logar erro explícito se a segunda falhar, permitindo reconciliação manual (o Kardex continua sendo a fonte de verdade auditável mesmo se o saldo cacheado divergir temporariamente).
- **Opção robusta (preferível se o tempo permitir):** criar uma função `RPC` no Postgres que faça as duas operações dentro de uma única transação (`INSERT` na movimentação + `UPDATE` do saldo), eliminando a janela de inconsistência.
Registrar a decisão tomada em Dev Agent Record.

### Tabela-alvo
`public.estoque_movimentacoes` (migration `20260921_initial_schema.sql` §7): `id TEXT PRIMARY KEY`, `peca_id TEXT REFERENCES pecas(id) ON DELETE CASCADE`, `tipo TEXT CHECK IN ('entrada','saida','ajuste')`, `quantidade INTEGER`, `motivo TEXT`, `documento_ref TEXT`, `usuario TEXT DEFAULT 'Sistema'`, `created_at`. **Nota:** esta tabela não tem `updated_at` (é append-only por natureza) — não se aplica o trigger da Story 2.2 aqui, exceto a trigger de auditoria (`fn_audit_trigger`), que a Story 2.2 já lista para esta tabela.

### RLS já existente
Apenas `"Admin total estoque"` (`FOR ALL`, admin). É a única tabela de domínio operacional sem política de leitura para a equipe — gap real a resolver nesta story.
