# Story 2.1: Fundação do Cliente Supabase e Camada de Repositório Assíncrona

**Autor:** River (@sm)

## Story

**Como** desenvolvedor responsável por migrar o `dev-oficina` de `localStorage` para Supabase Postgres,
**Quero** uma fundação comum de acesso a dados (cliente Supabase, mapeamento de campos, tratamento de erros fail-closed e estados de carregamento) reutilizável por todos os repositórios do domínio,
**Para que** cada story subsequente de migração (Ondas B a G) implemente apenas as particularidades da sua entidade, sem reinventar conexão, mapeamento `snake_case`↔`camelCase` ou tratamento de erro a cada vez, e sem reintroduzir o padrão de "sucesso falso" identificado no ADR-005.

---

## Escopo

**Dentro do escopo (IN):**
- Helpers de mapeamento de campos (`snake_case` ↔ `camelCase`).
- Wrapper de execução fail-closed (modo remoto vs. modo local, decidido uma única vez na inicialização).
- Classe/estrutura `ErroRepositorio` com códigos normalizados (ADR-005 §2.2).
- Rotina de limpeza de chaves `dev_oficina_*` no login/logout (ADR-005 §2.3).
- Extensão não-destrutiva de `src/lib/supabase.js`.
- Refatoração de `funcionariosRepository.js` como prova de conceito, incluindo checagem explícita de `{ error }`.

**Fora do escopo (OUT):**
- Migração de qualquer outro repositório de domínio (Ondas B–G, cada uma em sua própria story).
- Cache offline persistente (IndexedDB, fila de sincronização) — fora de escopo por decisão do ADR-005 §2.3; exigiria ADR próprio.
- RPCs transacionais específicas de entidade (tratadas nas stories que as usam: 2.8, 2.9, 2.19).
- Qualquer alteração de tela/UI.

## Acceptance Criteria

1. É criado um módulo utilitário `src/repositories/supabaseHelpers.js` (ou equivalente, ≤ 400 linhas) exportando funções puras de conversão `snake_case` (banco) ↔ `camelCase` (JS), reutilizadas por todos os repositórios que passarem a consumir Supabase.
2. É criado um wrapper padronizado de execução de queries (ex.: `executarOperacao(promiseSupabase, contexto)`) que implementa a política **fail-closed** do ADR-005 §2.1–§2.2:
   - o **modo de operação** (remoto vs. local) é decidido **uma única vez** na inicialização, a partir de `isSupabaseConfigured` e `import.meta.env.PROD` — nunca por chamada individual;
   - em **modo remoto** (`isSupabaseConfigured === true`), o wrapper checa tanto `{ error }` quanto o resultado esperado (ex.: `.select().single()` após `insert`/`update` para confirmar que a linha foi de fato afetada — um `UPDATE` bloqueado por RLS retorna 0 linhas **sem** erro) e lança `ErroRepositorio` (AC3) — **é proibido** qualquer fallback para `localStorage` motivado por falha de chamada (rede, RLS, constraint);
   - em **modo local** (dev/teste, `isSupabaseConfigured === false` **e** `import.meta.env.PROD === false`), o wrapper preserva o comportamento atual de leitura/gravação em `localStorage`;
   - build de **produção sem Supabase configurado** lança erro explícito na inicialização (mesmo princípio fail-closed já aplicado ao `AdminAuthContext` desde o commit `b006f0d`) — nunca cai silenciosamente para o modo local.
3. É criada a estrutura `ErroRepositorio` (ex.: `src/repositories/erroRepositorio.js`) com os códigos mínimos do ADR-005 §2.2 — `SEM_PERMISSAO`, `DUPLICADO`, `CONFLITO_EDICAO`, `FORA_DO_HORARIO`, `REFERENCIA_INVALIDA`, `INDISPONIVEL` —, mapeados a partir do `code` do PostgREST/Postgres, cada um com mensagem amigável correspondente para exibição via `sonner`. Todo `catch` tocado registra `console.error` com operação + entidade (PRD §4.4) antes de lançar o erro normalizado.
4. `src/lib/supabase.js` é estendido (sem quebrar a API pública atual — `supabase`, `isSupabaseConfigured`, `testarConexaoSupabase`) com um cliente de dados nomeado explicitamente (ex.: `getSupabaseDataClient()`) reaproveitando a mesma instância de `getSupabaseAdminClient()`, documentando que autenticação e dados usam a mesma sessão.
5. É definido e documentado em Dev Notes o **padrão de estados de UI assíncronos**: todo hook de domínio que consumir um repositório migrado deve expor `{ dados, carregando, erro }` (nomes em português, consistente com o idioma do domínio), onde `erro` carrega o `codigo` de `ErroRepositorio` quando aplicável; todo componente de tela deve tratar os três estados (loading sóbrio sem flash, mensagem de erro amigável via `sonner` `top-right`, dado vazio vs. indisponível).
6. É criado teste automatizado (Vitest) em `tests/unit/supabaseHelpers.test.js` cobrindo: conversão bidirecional de objetos aninhados simples; comportamento do wrapper em modo remoto lançando `ErroRepositorio` (sem gravar/ler `localStorage`) quando o Supabase retorna `{ error }` ou zero linhas afetadas; comportamento do wrapper em modo local (mock de `isSupabaseConfigured = false` e `PROD = false`); e log de erro em `console.error` em toda falha.
7. Nenhuma tela existente é alterada nesta story (fundação pura) — apenas `funcionariosRepository.js` é refatorado como prova de conceito para consumir os novos helpers **e para checar explicitamente `{ error }`/linhas afetadas em toda chamada Supabase hoje ignorada**, preservando 100% do comportamento observável em modo local e a interface pública documentada em ADR-002 (§3.1).
8. No login e no logout (fluxo de `AdminAuthContext`/autenticação), uma rotina de limpeza remove as chaves de domínio `dev_oficina_*` do `localStorage` (ADR-005 §2.3) — chaves de preferência de UI não pessoais podem permanecer; documentar a lista de chaves conhecidas na Dev Notes.
9. Todas as políticas RLS referenciadas ou criadas em qualquer Dev Notes desta e das próximas stories do Epic 2 usam exclusivamente `public.papel_usuario()` (app_metadata, ver migration `20260924130000_rls_papel_app_metadata.sql`). É **proibido** usar `auth.jwt() -> 'user_metadata'` em qualquer nova política — o documento `docs/architecture/supabase-persistence-model.md` está desatualizado nesse ponto (ver Dev Notes, Inconsistência 1) e não deve ser seguido literalmente.
10. `npm run lint` e `npm test` executam sem novos erros; nenhum arquivo novo ou modificado ultrapassa 400 linhas (NFR17).
11. Pré-requisito operacional registrado (não é código desta story, mas bloqueia o ambiente): as migrations `20260924120000_remover_dados_mock.sql` e `20260924130000_rls_papel_app_metadata.sql` devem estar aplicadas no projeto Supabase real antes de qualquer story da Onda B em diante ser desenvolvida contra um banco vivo; a rotação da senha do admin e a configuração dos secrets `SITE_URL`/`ALLOWED_ORIGINS` (pendências do usuário, fora do escopo de código) também são pré-condições operacionais.

## Dev Notes

### Contexto arquitetural
- **ADR-002** (`docs/architecture/project-decisions/adr-002-async-repository-layer-contracts.md`) já define o padrão *Async Contract First*: toda função de repositório retorna `Promise`. Esta story não altera esse contrato — apenas extrai a parte repetida de mapeamento/erro/fallback que hoje está duplicada inline em `funcionariosRepository.js`.
- **ADR-005** (`docs/architecture/project-decisions/adr-005-politica-acesso-dados-supabase.md`) é a referência normativa desta story: substitui o padrão de "fallback transparente em falha" (inseguro em produção multiusuário) pela política fail-closed descrita nos ACs 2–3. **Ler o ADR-005 §2.1–§2.3 por completo antes de implementar.**
- **Único repositório já consumindo Supabase hoje:** `src/repositories/funcionariosRepository.js` (280 linhas). Todos os demais (`clientesRepository.js`, `estoqueRepository.js`, `comprasRepository.js`, `suprimentosRepository.js`, `ordensServicoRepository.js`) leem/gravam exclusivamente em `localStorage` via `src/constants/*.js` — serão migrados nas Ondas B a F, cada um em sua própria story.
- **Cliente Supabase:** `src/lib/supabase.js` já expõe `supabase`, `isSupabaseConfigured`, `getSupabaseAdminClient()` e `testarConexaoSupabase()`. Não recriar — estender.

### Por que o padrão anterior mudou (ADR-005)
O padrão hoje replicado por `funcionariosRepository.js` (gravar primeiro no `localStorage`, depois chamar o Supabase sem checar `{ error }`, e usar `data.length > 0` como sinal de sucesso) produz **sucesso falso** em produção multiusuário: um `INSERT` negado pelo RLS aparece como salvo para o usuário, mas só existe no navegador dele. Com a remoção do FR14 (PRD v1.4), não há dado legado em `localStorage` a preservar — o fallback em falha não tem função em produção e é **proibido** a partir desta story.

### Inconsistências entre PRD/arquitetura e o código real (registrar, não corrigir aqui)
1. **RLS com `user_metadata` está obsoleto e inseguro.** `docs/architecture/supabase-persistence-model.md` (§3) e a migration original `20260921_initial_schema.sql` (§11) escrevem políticas usando `auth.jwt() -> 'user_metadata' ->> 'role'`. Isso foi corrigido na Fase 0 de segurança (commit `b006f0d`, migration `20260924130000_rls_papel_app_metadata.sql`), que introduziu `public.papel_usuario()` lendo `app_metadata` (gravável só pelo servidor). **Toda política nova do Epic 2 deve usar `public.papel_usuario()`.**
2. **IDs são `UUID` no documento de arquitetura, mas `TEXT` no banco real.** `supabase-persistence-model.md` (§2) modela `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`; a migration real `20260921_initial_schema.sql` usa `id TEXT PRIMARY KEY` em todas as tabelas. Esta e as próximas stories seguem o **código real (TEXT)**, com `DEFAULT gen_random_uuid()::text` para tabelas onde o ADR-005 §2.6 determina que o banco passa a gerar o ID.

### Tabelas já existentes no banco (migration `20260921_initial_schema.sql`, ajustada por `20260924120000` e `20260924130000`)
`funcionarios`, `clientes`, `veiculos`, `pecas`, `servicos`, `terceiros`, `estoque_movimentacoes`, `compras_pedidos`, `compras_cotacoes`, `ordens_servico` (com snapshots JSONB e itens em JSONB), `audit_logs`. Nenhum trigger existe ainda (ver Story 2.2).

### Padrão de Estados de UI Assíncronos (AC5)
Todo hook de domínio que consumir repositórios Supabase migrados deve expor o contrato canônico:
- `dados`: `T | null` (dados retornados da entidade ou null enquanto inicializando/erro).
- `carregando`: `boolean` (true durante qualquer tráfego de rede assíncrono).
- `erro`: `ErroRepositorio | Error | null` (carregando `erro.codigo` normalizado: `SEM_PERMISSAO`, `DUPLICADO`, `INDISPONIVEL`, etc.).

Os componentes de apresentação devem tratar explicitamente os 3 estados:
1. **Carregando:** feedback visual sóbrio (spinner ou skeleton sem flash de layout shift).
2. **Erro:** notificação amigável via `sonner` posicionado em `top-right`, exibindo a mensagem sanitizada do `ErroRepositorio`.
3. **Vazio vs. Indisponível:** feedback de "Nenhum registro encontrado" só quando `dados.length === 0` e `erro === null`; quando `erro !== null`, exibir estado de erro com ação de retry.

### Chaves `dev_oficina_*` conhecidas a limpar (AC8)
A limpeza de dados locais no `signIn`/`signOut` foi restrita estritamente às **entidades já migradas** para o Supabase (atualmente apenas `dev_oficina_funcionarios`). Módulos em migração nas Ondas B a G (`dev_oficina_clientes`, `dev_oficina_ordens_servico`, agenda, etc.) permanecem intactos no `localStorage` até suas histórias específicas de migração, prevenindo perda de dados (REL-002 / REQ-001). Chaves de preferência de UI (`dev_oficina_tema`, `dev_oficina_sidebar_colapsada`, etc.) são preservadas em definitivo.

### Riscos
- Abstrair cedo demais pode engessar as próximas stories; manter os helpers pequenos e genéricos (conversão de chave + wrapper de erro fail-closed), sem tentar prever todos os formatos de dado (ex.: JSONB) nesta fundação.
- Qualquer mudança em `funcionariosRepository.js` precisa preservar o fluxo de `criarLoginFuncionario()` (Edge Function `criar-login-funcionario`), que não deve ser tocado.
- A decisão de modo (remoto vs. local) "uma vez na inicialização" precisa ser cuidadosamente implementada para não recalcular por chamada — um bug aqui reintroduziria o comportamento inseguro que esta story elimina.
