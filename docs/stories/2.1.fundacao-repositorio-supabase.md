# Story 2.1: Fundação do Cliente Supabase e Camada de Repositório Assíncrona

**Autor:** River (@sm)

**Quality Gate:** @architect

## Story

**Como** desenvolvedor responsável por migrar o `dev-oficina` de `localStorage` para Supabase Postgres,
**Quero** uma fundação comum de acesso a dados (cliente Supabase, mapeamento de campos, tratamento de erros e estados de carregamento) reutilizável por todos os repositórios do domínio,
**Para que** cada story subsequente de migração (Ondas B a G) implemente apenas as particularidades da sua entidade, sem reinventar conexão, mapeamento `snake_case`↔`camelCase` ou tratamento de erro a cada vez.

---

## Acceptance Criteria

1. É criado um módulo utilitário `src/repositories/supabaseHelpers.js` (ou equivalente, ≤ 400 linhas) exportando funções puras de conversão `snake_case` (banco) ↔ `camelCase` (JS), reutilizadas por todos os repositórios que passarem a consumir Supabase.
2. É criado um wrapper padronizado de execução de queries (ex.: `executarComFallback(promiseSupabase, valorFallbackLocalStorage)`) que padroniza: (a) captura de erro do Supabase (`{ data, error }`), (b) log via `console.error` em todo `catch` tocado (conforme PRD §4.4), (c) fallback transparente para `localStorage` quando `isSupabaseConfigured` for `false` ou a chamada falhar — preservando o padrão já usado em `src/repositories/funcionariosRepository.js`.
3. `src/lib/supabase.js` é estendido (sem quebrar a API pública atual — `supabase`, `isSupabaseConfigured`, `testarConexaoSupabase`) com um cliente de dados nomeado explicitamente (ex.: `getSupabaseDataClient()`) reaproveitando a mesma instância de `getSupabaseAdminClient()`, documentando que autenticação e dados usam a mesma sessão.
4. É definido e documentado em Dev Notes o **padrão de estados de UI assíncronos**: todo hook de domínio que consumir um repositório migrado deve expor `{ dados, carregando, erro }` (nomes em português, consistente com o idioma do domínio) e todo componente de tela deve tratar os três estados (loading sóbrio sem flash, mensagem de erro amigável via `sonner` `top-right`, dado vazio vs. indisponível).
5. É criado teste automatizado (Vitest) em `tests/unit/supabaseHelpers.test.js` cobrindo: conversão bidirecional de objetos aninhados simples, wrapper de fallback com Supabase configurado e com Supabase indisponível (mock de `isSupabaseConfigured = false`), e log de erro em `console.error` quando a chamada Supabase falha.
6. Nenhuma tela existente é alterada nesta story (fundação pura) — apenas `funcionariosRepository.js` é refatorado como prova de conceito para consumir os novos helpers, preservando 100% do comportamento e da interface pública documentada em ADR-002 (§3.1).
7. Todas as políticas RLS referenciadas ou criadas em qualquer Dev Notes desta e das próximas stories do Epic 2 usam exclusivamente `public.papel_usuario()` (app_metadata, ver migration `20260924130000_rls_papel_app_metadata.sql`). É **proibido** usar `auth.jwt() -> 'user_metadata'` em qualquer nova política — o documento `docs/architecture/supabase-persistence-model.md` está desatualizado nesse ponto (ver Dev Notes, Inconsistência 1) e não deve ser seguido literalmente.
8. `npm run lint` e `npm test` executam sem novos erros; nenhum arquivo novo ou modificado ultrapassa 400 linhas (NFR17).
9. Pré-requisito operacional registrado (não é código desta story, mas bloqueia o ambiente): as migrations `20260924120000_remover_dados_mock.sql` e `20260924130000_rls_papel_app_metadata.sql` devem estar aplicadas no projeto Supabase real antes de qualquer story da Onda B em diante ser desenvolvida contra um banco vivo; a rotação da senha do admin e a configuração dos secrets `SITE_URL`/`ALLOWED_ORIGINS` (pendências do usuário, fora do escopo de código) também são pré-condições operacionais.

## Dev Notes

### Contexto arquitetural
- **ADR-002** (`docs/architecture/project-decisions/adr-002-async-repository-layer-contracts.md`) já define o padrão *Async Contract First*: toda função de repositório retorna `Promise`. Esta story não altera esse contrato — apenas extrai a parte repetida de mapeamento/erro/fallback que hoje está duplicada inline em `funcionariosRepository.js`.
- **Único repositório já consumindo Supabase hoje:** `src/repositories/funcionariosRepository.js` (280 linhas). Todos os demais (`clientesRepository.js`, `estoqueRepository.js`, `comprasRepository.js`, `suprimentosRepository.js`, `ordensServicoRepository.js`) leem/gravam exclusivamente em `localStorage` via `src/constants/*.js` — serão migrados nas Ondas B a F, cada um em sua própria story.
- **Cliente Supabase:** `src/lib/supabase.js` já expõe `supabase`, `isSupabaseConfigured`, `getSupabaseAdminClient()` e `testarConexaoSupabase()`. Não recriar — estender.

### Inconsistências entre PRD/arquitetura e o código real (registrar, não corrigir aqui)
1. **RLS com `user_metadata` está obsoleto e inseguro.** `docs/architecture/supabase-persistence-model.md` (§3) e a migration original `20260921_initial_schema.sql` (§11) escrevem políticas usando `auth.jwt() -> 'user_metadata' ->> 'role'`. Isso foi corrigido na Fase 0 de segurança (commit `b006f0d`, migration `20260924130000_rls_papel_app_metadata.sql`), que introduziu `public.papel_usuario()` lendo `app_metadata` (gravável só pelo servidor). **Toda política nova do Epic 2 deve usar `public.papel_usuario()`.** Recomenda-se ao `@architect`/`@po` atualizar `supabase-persistence-model.md` para não induzir a regressão de segurança em futuras leituras do documento.
2. **IDs são `UUID` no documento de arquitetura, mas `TEXT` no banco real.** `supabase-persistence-model.md` (§2) modela `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`; a migration real `20260921_initial_schema.sql` usa `id TEXT PRIMARY KEY` em todas as tabelas (compatível com os IDs gerados no front, ex.: `func-${Date.now()}`, `peca-001`). Esta story e as seguintes devem seguir o **código real (TEXT)**, não o documento de arquitetura.

### Tabelas já existentes no banco (migration `20260921_initial_schema.sql`, ajustada por `20260924120000` e `20260924130000`)
`funcionarios`, `clientes`, `veiculos`, `pecas`, `servicos`, `terceiros`, `estoque_movimentacoes`, `compras_pedidos`, `compras_cotacoes`, `ordens_servico` (com snapshots JSONB e itens em JSONB), `audit_logs`. Nenhum trigger existe ainda (ver Story 2.2).

### Arquivos afetados por esta story
- **[NEW]** `src/repositories/supabaseHelpers.js`
- **[MODIFY]** `src/lib/supabase.js` (adição não-destrutiva)
- **[MODIFY]** `src/repositories/funcionariosRepository.js` (refatoração interna, mesma API pública)
- **[NEW]** `tests/unit/supabaseHelpers.test.js`

### Riscos
- Abstrair cedo demais pode engessar as próximas stories; manter os helpers pequenos e genéricos (conversão de chave + wrapper de erro), sem tentar prever todos os formatos de dado (ex.: JSONB) nesta fundação.
- Qualquer mudança em `funcionariosRepository.js` precisa preservar o fluxo de `criarLoginFuncionario()` (Edge Function `criar-login-funcionario`), que não deve ser tocado.
